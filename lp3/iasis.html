1. Reenquadrando o problema

Antes de desenhar classes, a correção orientada recomenda transformar o enunciado em perguntas de engenharia: (1) quais são as entidades centrais; (2) onde existe variação; (3) como o sistema deve evoluir sem “quebrar tudo”; (4) onde pode surgir acoplamento excessivo. O objetivo não é maximizar quantidade de classes, mas decidir responsabilidades e controlar o impacto de mudanças futuras no núcleo do domínio.

Objetivo

Estabelecer um critério de correção: avaliar o modelo pelo controle da mudança, e não por volume de elementos.

O que se espera alcançar

Um raciocínio estruturado que separa domínio (estável) de infraestrutura (mutável), reduzindo acoplamento.

2. Passo 1 — Identificar as abstrações centrais do domínio

O núcleo do domínio da plataforma de assistente pessoal deve representar, no mínimo: o profissional (usuário), seus clientes, suas tarefas e os compromissos/eventos que podem estar associados a tarefas. A integração com serviços externos (agenda, mensageria) é importante, mas pertence à infraestrutura; por isso, deve permanecer separada do domínio. 

Diagrama UML 1 — Núcleo mínimo do domínio

+----------------+     +----------------+     +----------------+     +-------------------+
|    Usuario     |     |     Cliente    |     |     Tarefa     |     |   EventoAgenda    |
+----------------+     +----------------+     +----------------+     +-------------------+
| id             |     | id             |     | id             |     | id                |
| nome           |     | nome           |     | descricao      |     | inicio            |
+----------------+     +----------------+     | status         |     | fim               |
| ...            |     | ...            |     | prazo          |     | local             |
+----------------+     +----------------+     +----------------+     +-------------------+
Objetivo

Definir um conjunto mínimo de classes do domínio, evitando introduzir tecnologia (APIs externas) como se fosse parte do negócio.

O que se espera alcançar

Um domínio “sem tecnologia”: classes representam conceitos do mundo real, preservando independência de infraestrutura.

3. Passo 2 — Relacionar as classes com multiplicidades

O passo seguinte é estabelecer relações e multiplicidades, porque isso costuma revelar complexidade e decisões de regra de negócio. Em geral, um usuário gerencia vários clientes; um cliente possui várias tarefas; e algumas tarefas geram eventos de agenda. A correção destaca que o evento é opcional: nem toda tarefa vira compromisso. 

Diagrama UML 2 — Relações e multiplicidades

Usuario 1  --- gerencia --- 0..* Cliente
Cliente 1 --- possui    --- 0..* Tarefa
Tarefa  1 --- agenda    --- 0..1 EventoAgenda

Observação: EventoAgenda é opcional (0..1) porque nem toda tarefa vira compromisso.
Ponto de decisão.

Multiplicidades ajudam a explicitar perguntas de domínio: “tarefa sem cliente existe?” A resposta depende do modelo e das regras do contexto.

4. Passo 3 — Atribuir responsabilidades sem “inflar” o modelo

Nesta etapa, atribui-se a cada classe o mínimo coerente de estado e comportamento. A correção enfatiza evitar o padrão “objeto Deus” (colocar tudo em Usuario). Cada classe deve oferecer operações alinhadas à sua responsabilidade, preservando coesão. Também se destaca que Cliente não deveria conter métodos de “enviar mensagem” ou integração com WhatsApp; isso é infraestrutura. 

Diagrama UML 3 — Classes com atributos e operações essenciais (exemplo mínimo)

Usuario
  - id: String
  - nome: String
  + cadastrarCliente(c: Cliente)
  + criarTarefa(c: Cliente, t: Tarefa)

Cliente
  - id: String
  - nome: String
  - contato: String
  + adicionarTarefa(t: Tarefa)

Tarefa
  - id: String
  - descricao: String
  - status: String
  - prazo: DateTime
  + concluir()
  + reagendar(novoPrazo: DateTime)

EventoAgenda
  - id: String
  - inicio: DateTime
  - fim: DateTime
  - local: String

Pseudocódigo comentado (exemplo de coesão e encapsulamento)

O pseudocódigo a seguir ilustra um desenho mínimo coerente: Usuario gerencia agregação de clientes; Cliente gerencia suas tarefas; Tarefa controla transições básicas (concluir, reagendar). A intenção é concentrar regras onde a responsabilidade é natural. 

classe Usuario {
    privado clientes : Lista

    metodo cadastrarCliente(c: Cliente) {
        // responsabilidade: manter coleção de clientes do profissional
        clientes.adicionar(c)
    }

    metodo criarTarefa(c: Cliente, t: Tarefa) {
        // delegação: tarefa pertence ao cliente no domínio (pode variar conforme regra do curso)
        c.adicionarTarefa(t)
    }
}

classe Cliente {
    privado tarefas : Lista

    metodo adicionarTarefa(t: Tarefa) {
        tarefas.adicionar(t)
    }
}

classe Tarefa {
    privado status
    privado prazo

    metodo concluir() {
        status = "CONCLUIDA"
    }

    metodo reagendar(novoPrazo) {
        // regra mínima: novo prazo precisa ser futuro (exemplo)
        se (novoPrazo <= agora()) lançar ErroDominio("Prazo inválido")
        prazo = novoPrazo
    }
}
Nota de correção recorrente.

Se o domínio contiver chamadas diretas a APIs (WhatsApp, Google Calendar), o modelo fica preso à tecnologia e perde capacidade de troca futura.

5. Passo 4 — Identificar pontos de variação

A correção explicita pelo menos quatro frentes de variação: (i) adaptação conforme perfil do usuário; (ii) integrações com serviços externos; (iii) extensão para novos dispositivos/canais; e (iv) evolução futura (que engloba as anteriores). A medida prática de qualidade do modelo é: quando surgir uma mudança, ela deve ser absorvida por componentes adicionados, e não por reescrita do núcleo. 

Pontos de variação típicos:
1) Perfil do usuário (consultor, advogado, designer...)
2) Integrações externas (Google, Outlook, WhatsApp...)
3) Dispositivos / canais (mobile, smartwatch, voz...)
4) Novas funcionalidades de IA (recomendação, automação)
Objetivo

Tornar explícito onde o sistema tende a mudar, antes de escolher herança, interfaces ou composição.

O que se espera alcançar

Um “mapa” de evolução: domínio estável + pontos de extensão que absorvem mudança inevitável.

6. Passo 5 — Variação 1: Perfil do usuário como Strategy

A correção recomenda evitar herança para perfis (UsuarioConsultor, UsuarioAdvogado etc.), pois perfil tende a ser comportamento, não identidade estrutural. Além disso, perfis podem crescer e combinar. A alternativa é o usuário possuir uma estratégia associada ao perfil. 

Diagrama UML 4 — Perfil como Strategy

Usuario
  - perfil : PerfilProfissional
  + sugerirProximasAcoes() : String[]

PerfilProfissional (interface)
  + sugerirTarefasContextuais(u: Usuario) : String[]
  + regrasDeAtendimento() : String

Implementações:
  PerfilConsultor, PerfilAdvogado, PerfilDesigner

Ideia: o usuário não é um perfil; ele tem um perfil (estratégia).

Pseudocódigo comentado (Strategy)

No desenho abaixo, Usuario depende apenas do contrato PerfilProfissional. Para adicionar um novo perfil, cria-se uma nova implementação, sem modificar a classe Usuario. 

interface PerfilProfissional {
    metodo sugerirTarefasContextuais(u: Usuario) : Lista
    metodo regrasDeAtendimento() : String
}

classe PerfilConsultor implementa PerfilProfissional {
    metodo sugerirTarefasContextuais(u) {
        retornar ["Preparar proposta", "Revisar contrato", "Agendar follow-up"]
    }
    metodo regrasDeAtendimento() { retornar "Atendimento por sessão; registrar decisões." }
}

classe Usuario {
    privado perfil : PerfilProfissional

    metodo sugerirProximasAcoes() {
        retornar perfil.sugerirTarefasContextuais(this)
    }
}

7. Passo 6 — Variação 2: Integrações externas por interfaces (Ports & Adapters)

Integrações com agenda e mensageria mudam com frequência. Se o domínio conhecer diretamente Google Calendar, ficará preso a essa tecnologia. A correção propõe contratos (interfaces) e implementações como adaptadores. Se surgir Outlook, adiciona-se um novo adaptador, sem alterar o domínio. 

Diagrama UML 5 — Integração com agenda e mensageria por interfaces

IntegracaoAgenda (interface)
  + criarEvento(e: EventoAgenda)
  + atualizarEvento(e: EventoAgenda)

Implementações (adapters):
  GoogleCalendarAdapter
  OutlookCalendarAdapter

IntegracaoMensageria (interface)
  + enviarMensagem(destino: String, msg: String)

Implementações (adapters):
  EmailAdapter
  WhatsAppAdapter

Pseudocódigo comentado (adapters)

O serviço de aplicação (camada acima do domínio) pode depender das interfaces de integração. As classes de domínio não devem invocar APIs externas diretamente. 

interface IntegracaoAgenda {
    metodo criarEvento(e: EventoAgenda)
}

classe GoogleCalendarAdapter implementa IntegracaoAgenda {
    metodo criarEvento(e) {
        // chamada para API do Google (infraestrutura)
    }
}

classe OutlookCalendarAdapter implementa IntegracaoAgenda {
    metodo criarEvento(e) {
        // chamada para API do Outlook (infraestrutura)
    }
}

// Serviço de aplicação (orquestra, não é "domínio puro")
classe ServicoAgenda {
    privado agenda : IntegracaoAgenda

    metodo agendarCompromisso(e: EventoAgenda) {
        agenda.criarEvento(e)
    }
}
Pergunta de correção típica.

Se o grupo desenhou “Usuario → GoogleCalendar”, o que acontece quando o cliente pede Outlook? Se a resposta for “preciso editar várias classes”, há acoplamento excessivo.

8. Passo 7 — Variação 3: Canais e dispositivos (interfaces de notificação)

O enunciado exige extensão futura para novos dispositivos. A correção trata isso como ponto de variação clássico: o sistema produz notificações, mas o canal pode variar (mobile, smartwatch, voz). Introduz-se um contrato CanalNotificacao. Adicionar um novo dispositivo significa criar uma nova implementação, sem alterar o restante. 

Diagrama UML 6 — CanalNotificacao como ponto de extensão

ServicoNotificacao
  - canal : CanalNotificacao
  + notificar(u: Usuario, msg: String)

CanalNotificacao (interface)
  + enviar(destino: Usuario, msg: String)

Implementações:
  NotificacaoMobile
  NotificacaoSmartwatch
  NotificacaoVoz

Pseudocódigo comentado (canais)

interface CanalNotificacao {
    metodo enviar(destino: Usuario, msg: String)
}

classe NotificacaoMobile implementa CanalNotificacao {
    metodo enviar(destino, msg) { /* push no app */ }
}

classe NotificacaoVoz implementa CanalNotificacao {
    metodo enviar(destino, msg) { /* saída por assistente de voz */ }
}

classe ServicoNotificacao {
    privado canal : CanalNotificacao

    metodo notificar(u: Usuario, msg: String) {
        canal.enviar(u, msg)
    }
}

9. Passo 8 — Consolidar a solução: visão integrada

A correção recomenda consolidar o modelo em uma visão arquitetural integrada composta por quatro blocos conectados: (1) domínio (Usuario–Cliente–Tarefa–EventoAgenda); (2) perfil como estratégia; (3) integrações externas por interfaces; (4) canais/dispositivos por interfaces. O objetivo é responder: onde o sistema é estável e onde ele precisa ser flexível. 

Diagrama UML 7 — Visão integrada (resumo)

[Domínio]
Usuario 1 -- 0..* Cliente 1 -- 0..* Tarefa 1 -- 0..1 EventoAgenda

[Pontos de variação]
Usuario possui PerfilProfissional (Strategy)
ServicoAgenda usa IntegracaoAgenda (Interface -> Adapters)
ServicoMensageria usa IntegracaoMensageria (Interface -> Adapters)
ServicoNotificacao usa CanalNotificacao (Interface -> Implementações)

Princípio: domínio é o que permanece; interfaces e estratégias absorvem mudança.
Regra operacional de extensibilidade.

Se amanhã for necessário adicionar um novo perfil profissional, um novo provedor de agenda ou um novo dispositivo, o modelo deve permitir isso por adição de componentes, sem modificar as entidades centrais do domínio.

10. Passo 9 — Onde há risco de acoplamento excessivo

A correção sugere perguntas diagnósticas para avaliar separação entre responsabilidades e níveis de abstração. Em um bom modelo, o domínio permanece estável, enquanto elementos sujeitos a mudança (integrações, perfis, canais) são isolados por abstrações apropriadas. 

1) Dependência direta do domínio em tecnologias externas:
   - Usuario/Cliente/Tarefa chamam APIs (Google Calendar, WhatsApp, e-mail)?
   -> Se sim, domínio ficou acoplado.

2) Uso inadequado de herança para perfis:
   - Existem muitas subclasses de Usuario para perfis profissionais?
   -> Indício de rigidez e baixa escalabilidade.

3) Dependência de um único canal:
   - Notificação acoplada apenas a mobile?
   -> Novos dispositivos exigirão mudanças espalhadas.

4) Classe central com responsabilidades excessivas (God Object):
   - Uma classe faz: usuários + comunicação externa + agenda + regras de negócio?
   -> Baixa coesão e alto acoplamento.
Objetivo

Oferecer critérios objetivos para avaliar modelos: sinais práticos de acoplamento, rigidez e baixa coesão.

O que se espera alcançar

Que o estudante consiga “diagnosticar” fragilidades estruturais a partir do diagrama, antes da implementação.

11. Passo 10 — Checklist final de qualidade da modelagem

A análise do modelo pode ser conduzida por critérios estruturais que indicam baixo acoplamento, alta coesão e capacidade de evolução. O checklist abaixo sintetiza os critérios finais apresentados na correção. 

• Independência do domínio em relação à infraestrutura
  - Usuario/Cliente/Tarefa não dependem diretamente de APIs específicas.

• Representação explícita dos pontos de variação
  - Perfis, integrações e canais modelados por interfaces/estratégias.

• Extensibilidade por adição de componentes
  - Evolução ocorre criando novas classes/implementações, não alterando o núcleo.

• Distribuição adequada de responsabilidades
  - Evitar God Object; cada classe com propósito claro.

• Isolamento de comportamentos variáveis
  - Aspectos com alta probabilidade de mudança encapsulados em contratos.

• Foco no controle da mudança arquitetural
  - Mudanças futuras devem ter impacto limitado e previsível.
