v4.0 GitHub – Guia Didático Completo

Fundamentos teóricos de Git, grafo de commits (Mermaid), conflitos reais, Git Flow e automação com GitHub Actions

Material desenhado para leitura gradual: conceitos → modelo mental → prática → governança → automação.

1. Controle de versão: por que existe e o que o Git resolve

Controle de versão é um mecanismo para registrar, auditar e recuperar estados históricos de um artefato (código, texto, dados, configuração). A motivação não é apenas “voltar no tempo”, mas garantir reprodutibilidade e coordenação quando múltiplas pessoas alteram os mesmos arquivos.

Em sistemas centralizados, um servidor é o ponto de verdade. No Git, o versionamento é distribuído: cada clone contém o histórico completo. Isso reduz acoplamento com infraestrutura, melhora resiliência e permite trabalho offline.

Modelo mental: o Git é um banco de dados de “snapshots” identificados por hashes; GitHub é a plataforma que hospeda esse banco e adiciona governança (PRs, issues, review, CI/CD).

2. Arquitetura interna do Git: objetos e o “grafo de commits”

O Git armazena objetos endereçados por conteúdo (content-addressable). O identificador (hash) de um objeto depende do conteúdo. Alterou o conteúdo, muda o hash; isso dá integridade e rastreabilidade.

Os principais objetos são blob (conteúdo de arquivo), tree (estrutura de diretórios), commit (metadados + ponteiros para tree e pais), e tag (referência nomeada, frequentemente para releases).

2.1. O grafo de commits como estrutura de dados

Um repositório Git é um grafo acíclico direcionado (DAG): cada commit aponta para seu(s) commit(s) pai(s). Merge cria commits com dois pais, conectando ramos. 

gitGraph
  commit id:"A"
  commit id:"B"
  branch feature
  checkout feature
  commit id:"C"
  commit id:"D"
  checkout main
  commit id:"E"
  merge feature id:"M"

Leitura do diagrama: main evolui A→B→E; a branch feature evolui C→D; o commit M é o merge (dois pais), preservando a história dos dois ramos. 

git log --graph --oneline --decorate --all

Esse comando aproxima o diagrama acima no terminal.

3. O fluxo de estados: Working Directory → Staging → Repository

O Git separa “o que você está editando” do “o que você pretende registrar”. Isso permite compor commits com granularidade técnica adequada (coerência semântica). 

flowchart LR
  WD["Working Directory
arquivos editáveis"] -->|git add| ST["Staging Area
o que vai entrar no commit"]
  ST -->|git commit| REPO["Local Repository (.git)
histórico (DAG)"]
  REPO -->|git push| REM["Remote (GitHub)
cópia compartilhada"]
  REM -->|git fetch/pull| REPO
Didática do staging: staging é um “rascunho do commit”. Você pode selecionar pedaços de alteração para entrar no snapshot final. 
git status
git add -p        # adiciona por partes (hunks), excelente para commits limpos
git commit -m "Explica claramente o porquê da mudança"

4. Branches, merge e rebase: quando usar e por quê

Uma branch é um ponteiro para um commit; criar branch é barato e não duplica o repositório. O valor das branches é organizacional: isolar trabalho, reduzir risco e facilitar revisão.

4.1. Merge (preserva história) vs Rebase (reescreve história)

gitGraph
  commit id:"A"
  commit id:"B"
  branch feature
  checkout feature
  commit id:"C"
  commit id:"D"
  checkout main
  commit id:"E"
  merge feature id:"M"

Merge: preserva estrutura do DAG (útil para auditoria e rastreabilidade).

git checkout main
git merge feature
gitGraph
  commit id:"A"
  commit id:"B"
  branch feature
  checkout feature
  commit id:"C"
  commit id:"D"
  checkout main
  commit id:"E"
  checkout feature
  commit id:"C'"
  commit id:"D'"
  checkout main
  merge feature id:"F"

Rebase: “reaplica” commits sobre outra base, produzindo histórico mais linear, mas alterando hashes. Evite rebase em branches já compartilhadas. 

git checkout feature
git rebase main
Regra prática: rebase é ótimo para limpar sua branch local antes de abrir PR; merge é mais seguro para integrar trabalho compartilhado sem reescrever histórico.

5. Fork + Upstream: colaboração em projetos externos (modelo open source)

Fork cria uma cópia do repositório original sob sua conta no GitHub. Isso permite contribuir sem permissões de escrita no repositório principal. O conceito-chave é a distinção entre:

  • origin: seu fork (onde você tem permissão)
  • upstream: repositório original (fonte de verdade)
flowchart LR
  U["upstream
repo original"] -->|fork (GitHub)| F["seu fork
repo na sua conta"]
  F -->|git clone| L["seu computador
repo local"]
  L -->|git push| F
  F -->|Pull Request| U
  U -->|atualizações| F
          
# 1) Clonar seu fork
git clone https://github.com/SEU_USUARIO/projeto.git
cd projeto

# 2) Registrar upstream
git remote add upstream https://github.com/ORIGINAL/projeto.git

# 3) Atualizar sua main com upstream
git checkout main
git fetch upstream
git merge upstream/main
git push origin main
Por que isso importa? Em projetos grandes, sua cópia precisa acompanhar o ritmo do upstream; manter seu fork sincronizado reduz conflitos e simplifica PRs.

6. Conflitos reais: diagnóstico, resolução e prevenção

Conflitos ocorrem quando o Git não consegue combinar automaticamente alterações que tocam as mesmas linhas (ou regiões) de um arquivo. Isso não é “erro”: é uma sinalização de ambiguidade semântica que exige decisão humana.

6.1. Cenário típico de conflito

Dois ramos alteram a mesma função calcular_total(). Ao integrar, o Git detecta que as duas versões divergem no mesmo trecho. 

gitGraph
  commit id:"A"
  branch feature_desconto
  checkout feature_desconto
  commit id:"B (desconto)"
  checkout main
  branch hotfix_imposto
  checkout hotfix_imposto
  commit id:"C (imposto)"
  checkout main
  merge feature_desconto id:"M1"
  merge hotfix_imposto id:"M2"

6.2. Como o conflito aparece no arquivo

<<<<<<< HEAD
total = subtotal * 1.10   # hotfix: imposto 10%
=======
total = subtotal - desconto # feature: aplica desconto
>>>>>>> feature_desconto

O bloco acima indica duas versões concorrentes. Você deve produzir uma terceira versão coerente (por exemplo, aplicar desconto e depois imposto, ou o inverso, conforme a regra de negócio).

6.3. Passo a passo de resolução (prático)

# 1) Traga a base mais recente
git checkout main
git pull origin main

# 2) Tente integrar a branch (ex.: feature)
git merge feature_desconto

# 3) O Git reporta conflito. Inspecione:
git status

# 4) Abra o arquivo com conflito e decida a regra correta.
#    Remova os marcadores <<<<<<< ======= >>>>>>>

# 5) Marque como resolvido e finalize
git add arquivo_com_conflito.py
git commit -m "Resolve conflito: desconto + imposto"
git push origin main

6.4. Resolução assistida por ferramentas (recomendado)

Para equipes, é prática comum resolver conflitos no editor (VS Code) usando “Accept Current / Incoming / Both / Compare Changes”. O objetivo é reduzir erros ao editar manualmente.

6.5. Prevenção e redução de conflitos

  • Integre cedo e frequentemente (branches curtas).
  • PRs pequenos (mudanças menores são mais fáceis de combinar).
  • Modularize código: reduzir “pontos quentes” editados por todos.
  • Sincronize antes de começar: git pull ou git fetch + rebase/merge.
Cuidado: resolver conflito “no automático” sem entender a regra de negócio pode introduzir bugs silenciosos (o código compila, mas a lógica fica incorreta).

7. Git Flow formal: estrutura de branches e releases

Git Flow é uma convenção de ramificação que organiza desenvolvimento, estabilização e releases. É útil em equipes com ciclos de release definidos, mas pode ser pesado para times pequenos ou produtos com deploy contínuo.

7.1. Papéis formais das branches

  • main: produção (releases)
  • develop: integração contínua para próxima release
  • feature/*: desenvolvimento de funcionalidades
  • release/*: congelamento para estabilização e versionamento
  • hotfix/*: correções críticas em produção
gitGraph
  commit id:"v1.0" tag:"v1.0"
  branch develop
  checkout develop
  commit id:"D1"
  branch feature_login
  checkout feature_login
  commit id:"F1"
  commit id:"F2"
  checkout develop
  merge feature_login id:"MF"
  commit id:"D2"
  branch release_1_1
  checkout release_1_1
  commit id:"R1"
  checkout main
  merge release_1_1 id:"v1.1" tag:"v1.1"
  checkout develop
  merge release_1_1 id:"back-merge"
  branch hotfix_1_1_1
  checkout hotfix_1_1_1
  commit id:"H1"
  checkout main
  merge hotfix_1_1_1 id:"v1.1.1" tag:"v1.1.1"
  checkout develop
  merge hotfix_1_1_1 id:"sync-hotfix"

7.2. Sequência operacional mínima (comandos)

# iniciar desenvolvimento contínuo
git checkout -b develop main
git push -u origin develop

# iniciar uma feature
git checkout develop
git checkout -b feature/minha-feature

# finalizar feature (merge em develop)
git checkout develop
git merge --no-ff feature/minha-feature
git push origin develop

# iniciar release
git checkout develop
git checkout -b release/1.2.0

# finalizar release
git checkout main
git merge --no-ff release/1.2.0
git tag v1.2.0
git push origin main --tags

# back-merge para develop
git checkout develop
git merge --no-ff release/1.2.0
git push origin develop
Observação: em ambientes com CI/CD e deploy contínuo, muitas equipes preferem “trunk-based development” (main curta) com feature flags. Git Flow ainda é valioso quando existe fase explícita de estabilização (release branches).

8. GitHub Actions: CI/CD com exemplos e leitura técnica

GitHub Actions automatiza atividades do ciclo de engenharia: build, testes, lint, segurança e deploy. O arquivo YAML define eventos (on), jobs (jobs) e steps (steps).

8.1. Pipeline de CI para Python (comentado)

name: CI (Python)

on:
  push:
    branches: [ "main" ]       # roda quando há push em main
  pull_request:
    branches: [ "main" ]       # roda em PRs contra main

jobs:
  tests:
    runs-on: ubuntu-latest     # runner do GitHub (VM Linux)

    steps:
      - name: Checkout do código
        uses: actions/checkout@v4

      - name: Configura Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Instala dependências
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Executa testes
        run: |
          pytest -q

8.2. Segredos (Secrets) e variáveis

Para tokens e credenciais, utilize Settings → Secrets and variables → Actions. No workflow, injete via secrets.NOME. 

- name: Deploy (exemplo)
  env:
    API_TOKEN: ${{ secrets.API_TOKEN }}
  run: |
    echo "Token disponível apenas em runtime"
Boa prática: nunca versionar credenciais em arquivos. Use secrets e proteja branches (branch protection) para exigir CI verde antes do merge.

9. Checklist operacional: do zero até o PR com qualidade

  1. Sincronizar base: git pull ou git fetch
  2. Criar branch: git checkout -b feature/x
  3. Comitar em unidades coerentes (use git add -p)
  4. Abrir PR com descrição técnica (o quê + por quê + como testar)
  5. Garantir Actions verde (testes e lint)
  6. Revisar e ajustar
  7. Merge seguindo política do repositório
Meta do processo: tornar mudanças pequenas, verificáveis, rastreáveis e reversíveis.
