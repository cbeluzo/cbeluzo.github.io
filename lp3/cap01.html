1. Complexidade como problema estrutural

A orientação a objetos não deve ser compreendida primariamente como um conjunto de recursos sintáticos, mas como uma resposta teórica e prática ao problema de organizar a complexidade em sistemas de larga escala. Em sistemas contemporâneos, a dificuldade central raramente é “escrever código”, mas estruturar responsabilidades e dependências de modo que o sistema permaneça compreensível, verificável e evolutivo ao longo do tempo.

Na tradição da análise e do projeto orientados a objetos, a modelagem enfatiza entidades relevantes do domínio e seus papéis (responsabilidades), bem como as relações e variações de comportamento. Booch defende que a modelagem orientada a objetos desloca o foco da sequência de procedimentos para a estrutura de abstrações e colaborações. Meyer, ao formular o Design by Contract, enfatiza que classes devem explicitar e proteger regras que garantem consistência comportamental. Martin reforça que decisões estruturais determinam manutenibilidade, e Liskov formaliza a substituibilidade necessária para hierarquias semanticamente válidas.

Ideia central.

Orientação a objetos é um modelo mental para organizar sistemas complexos por responsabilidades e contratos, antes de ser um estilo de codificação.

2. Abstração e classe como unidade de responsabilidade

Considere um cenário de plataforma de streaming com personalização por recomendação. Um primeiro passo de modelagem é identificar abstrações fundamentais, isto é, entidades do domínio com propriedades e comportamentos coerentes. Abstrair, nesse contexto, consiste em capturar características essenciais e excluir detalhes acidentais, de forma a permitir raciocínio estável sobre o sistema.

Diagrama estrutural inicial (abstrações principais)

+----------------+
|    Usuário     |
+----------------+
| id             |
| perfil         |
| histórico      |
+----------------+
| consumir()     |
| recomendar()   |
+----------------+

+----------------+
|   Conteúdo     |
+----------------+
| título         |
| duração        |
| classificação  |
+----------------+
| exibir()       |
| calcularRel()  |
+----------------+
Objetivo do exemplo

Compreender que classe representa uma abstração com estado e comportamento integrados sob uma responsabilidade, e não apenas um “molde de dados”.

O que se espera alcançar

Que o estudante consiga justificar a presença de atributos e métodos como parte de uma decisão de modelagem: “quem sabe o quê” e “quem faz o quê” no domínio.

Exemplo com pseudocódigo: responsabilidade de registrar consumo

O comportamento “registrar consumo” pertence naturalmente ao usuário, pois se relaciona ao histórico e a regras de consistência (por exemplo, evitar duplicações ou registrar apenas conteúdos válidos). Ao concentrar esse comportamento na entidade responsável, reduz-se o risco de regras dispersas, o que tende a fragilizar a evolução do sistema. 

// Classe que representa a entidade Usuário
classe Usuario {

    privado historicoConsumo

    // Método responsável por registrar o consumo de um conteúdo
    metodo consumir(conteudo) {

        // Regra de negócio: impedir duplicação no histórico
        se (!historicoConsumo.contem(conteudo)) {
            historicoConsumo.adicionar(conteudo)
        }
    }

    metodo recomendar() {
        // Em versões futuras, delegar para uma estratégia de recomendação
    }
}

Observação conceitual: em uma perspectiva de contrato (Meyer), o método consumir é um ponto natural para impor pré-condições (conteúdo válido) e preservar invariantes (consistência do histórico).

3. Encapsulamento como garantia de coesão

Encapsulamento é frequentemente reduzido à ideia de ocultar atributos. Contudo, seu papel conceitual é preservar invariantes do domínio, isto é, condições que devem permanecer verdadeiras ao longo do ciclo de vida do objeto. Se regras forem aplicadas por múltiplos componentes externos, a classe perde controle sobre sua consistência, e o sistema passa a depender de disciplina informal — o que é frágil em sistemas reais.

Diagrama: responsabilidade concentrada no Usuário

+----------------+
|    Usuário     |
+----------------+
| histórico      |
+----------------+
| consumir()     |
| validar()      |
+----------------+
Objetivo do exemplo

Demonstrar que encapsulamento é a proteção de invariantes e a manutenção de coesão, e não apenas “esconder variáveis”.

O que se espera alcançar

Que o estudante identifique onde regras de negócio devem residir e reconheça que a dispersão de regras aumenta fragilidade e custo de mudança.

Exemplo com pseudocódigo: validação como proteção de invariantes

A validação pode ser tratada como parte do contrato da classe. A ideia é que o objeto imponha condições mínimas para preservar sua consistência. Em termos de projeto, isso reduz dependências externas e torna o comportamento previsível sob uma interface estável. 

// Exemplo: encapsulamento de validações na própria entidade
classe Usuario {

    privado historico

    metodo consumir(conteudo) {

        // Pré-condição: conteúdo deve ser válido
        validarConteudo(conteudo)

        // A atualização do histórico é responsabilidade do próprio Usuário
        historico.adicionar(conteudo)
    }

    metodo validarConteudo(conteudo) {
        se (conteudo == nulo) {
            lançar ErroDominio("Conteúdo inválido")
        }
    }
}

4. Herança: generalização estrutural e limites

Herança é um mecanismo de generalização estrutural: permite expressar que certos tipos especializados compartilham estado e comportamento de uma abstração mais geral. A interpretação conceitual adequada é a relação “é-um” (subtipo). Por exemplo, “Filme é um Conteúdo” expressa identidade estrutural: um filme pode ser tratado como conteúdo quando o sistema opera em termos gerais.

Diagrama: Conteúdo e especializações

           Conteúdo
              |
    ------------------------
    |          |           |
  Filme       Série       Live
Critério semântico.

Em termos do princípio de substituição de Liskov, uma subclasse deve preservar propriedades esperadas da superclasse. Herança deixa de ser apropriada quando a especialização viola expectativas comportamentais do tipo mais geral.

Objetivo do exemplo

Compreender herança como generalização estrutural coerente (subtipagem), e não como “recurso para reaproveitar código”.

O que se espera alcançar

Que o estudante saiba avaliar se uma hierarquia é semanticamente válida, distinguindo identidade de variação comportamental.

Exemplo com pseudocódigo: polimorfismo em cálculo de relevância

Considere a necessidade de calcular relevância de conteúdos para recomendação. Diferentes tipos podem adotar critérios distintos, porém o sistema deseja operar por meio de uma interface comum (calcularRelevancia). Polimorfismo permite que cada tipo responda à mesma mensagem com comportamento apropriado, sem condicionais espalhados. 

// Classe geral: Conteúdo
classe Conteudo {

    // Método definido no tipo geral (interface comum)
    metodo calcularRelevancia() {
        retornar 0
    }
}

// Especialização: Filme
classe Filme herda Conteudo {

    // Relevância baseada, por exemplo, em avaliações
    metodo calcularRelevancia() {
        retornar mediaAvaliacoes()
    }
}

// Especialização: Série
classe Serie herda Conteudo {

    // Relevância baseada, por exemplo, em retenção (episódios assistidos)
    metodo calcularRelevancia() {
        retornar taxaRetencao()
    }
}

5. Problemas da herança excessiva

Embora poderosa, herança cria uma relação estrutural forte. Em sistemas reais, o uso indiscriminado tende a produzir rigidez arquitetural. A literatura de projeto enfatiza que decisões estruturais devem considerar evolução futura e custo de mudança. O ponto central é que herança é adequada para identidade estrutural estável, mas frequentemente é usada indevidamente para modelar variações combinatórias de comportamento.

5.1 Acoplamento estrutural rígido

Diagrama: hierarquia profunda e dependência vertical

Conteúdo
  |
  +-- Filme
        |
        +-- FilmePremium

Em hierarquias profundas, mudanças na superclasse podem impactar várias subclasses. Esse efeito é um caso típico de acoplamento estrutural: a evolução de um conceito “central” tende a propagar-se para especializações, elevando o risco de regressões e exigindo refatorações amplas. Martin discute, em termos arquiteturais, que dependências mal posicionadas reduzem a elasticidade do sistema.

5.2 Explosão combinatória de subclasses

Diagrama: combinação de variações como subclasses

FilmeInterativo
SerieInterativa
LiveInterativa
FilmePremium
SeriePremium
LivePremium

Quando características como “premium”, “offline” ou “interativo” são tratadas como tipos fundamentais, a hierarquia tende a crescer por combinação. Isso torna o modelo difícil de compreender e manter. O problema decorre de representar comportamento variável como identidade.

5.3 Confusão entre identidade e comportamento

“Filme” costuma ser identidade estrutural (“é-um conteúdo”). Já “premium” e “offline” tendem a representar políticas de acesso ou capacidades, isto é, variações de comportamento. Ao usar herança para comportamento variável, perde-se clareza semântica e aumenta-se rigidez.

Síntese conceitual.

Herança é apropriada para identidade estrutural estável. Para comportamento variável, a tendência arquitetural mais robusta é separar o comportamento em componentes/estratégias (composição).

6. Composição e estratégias como alternativa arquitetural

Quando o comportamento pode variar independentemente da identidade estrutural, a composição tende a oferecer maior extensibilidade. Em termos de projeto, isso significa que o objeto “tem-um” componente responsável por uma política (estratégia), em vez de “ser-um” tipo específico rigidamente codificado na hierarquia. Essa abordagem se alinha ao princípio de dependência em abstrações (Martin) e reduz a necessidade de modificar classes centrais quando novas variações surgem.

Diagrama: estratégia de recomendação (contrato + implementações)

+----------------------+
| EstrategiaRecomend.  |
+----------------------+
| recomendar()         |
+----------------------+

       ▲
       |
------------------------------
|            |               |
Historico  Popularidade   Cluster

Diagrama: Usuário compõe uma estratégia

+----------------+
|    Usuário     |
+----------------+
| estrategia     |
+----------------+
| recomendar()   |
+----------------+
Objetivo do exemplo

Evidenciar a separação entre estrutura (identidade do objeto) e comportamento variável (políticas), por meio de interfaces/contratos.

O que se espera alcançar

Que o estudante compreenda como estratégias reduzem acoplamento e tornam o sistema extensível sem crescimento hierárquico.

Exemplo com pseudocódigo: usuário delega recomendação

A classe Usuário passa a depender apenas de um contrato (EstrategiaRecomendacao) e não de implementações específicas. Isso permite introduzir novos algoritmos (por exemplo, baseados em aprendizado de máquina) sem reescrever a classe Usuário. 

// Contrato: define o que significa "recomendar"
interface EstrategiaRecomendacao {
    metodo recomendar(usuario)
}

// Implementação 1: baseada em histórico
classe RecomendacaoPorHistorico implementa EstrategiaRecomendacao {

    metodo recomendar(usuario) {
        // Política: derivar recomendações do histórico do usuário
        retornar analisarHistorico(usuario)
    }
}

// Implementação 2: baseada em popularidade
classe RecomendacaoPorPopularidade implementa EstrategiaRecomendacao {

    metodo recomendar(usuario) {
        // Política: recomendar itens mais consumidos globalmente
        retornar listarMaisPopulares()
    }
}

// Usuário compõe uma estratégia e delega o comportamento variável
classe Usuario {

    privado estrategia

    metodo definirEstrategia(e) {
        estrategia = e
    }

    metodo recomendar() {
        // Delegação: Usuário não "sabe" como recomendar; ele delega para a estratégia
        retornar estrategia.recomendar(this)
    }
}

7. Polimorfismo e ligação dinâmica

Polimorfismo permite que diferentes objetos respondam à mesma mensagem por meio de uma interface comum. Em termos operacionais, a decisão sobre qual implementação executar ocorre em tempo de execução (ligação dinâmica). Isso é particularmente relevante para extensibilidade: o sistema pode ser estendido com novos tipos sem necessidade de modificar o código que opera sobre o tipo geral.

Diagrama: polimorfismo em Conteúdo

Conteúdo
   |
----------------
|      |       |
Filme Série   Live

Chamada polimórfica (mesma mensagem, comportamentos distintos)

listaConteudos.calcularRelevancia()
Objetivo do exemplo

Demonstrar como polimorfismo substitui condicionais estruturais e apoia o princípio aberto-fechado (extensão sem modificação).

O que se espera alcançar

Que o estudante consiga explicar, conceitualmente, por que a ligação dinâmica melhora extensibilidade e reduz complexidade de controle.

Exemplo com pseudocódigo: eliminando condicionais

Em vez de centralizar decisões em estruturas condicionais (que crescem a cada novo tipo), o sistema chama um método comum definido no tipo geral. Cada subtipo fornece sua própria implementação. Isso concentra variações nos próprios tipos e reduz a necessidade de alterar código existente ao introduzir novos tipos. 

// Operação em termos do tipo geral
metodo ranquearConteudos(listaDeConteudos) {

    para cada c em listaDeConteudos {
        // A mesma mensagem é enviada a objetos possivelmente diferentes
        score = c.calcularRelevancia()
        registrar(score)
    }

    retornar ordenarPorScore()
}
