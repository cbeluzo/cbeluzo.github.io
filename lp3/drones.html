1. Retomada do problema

O sistema em análise é uma plataforma de entregas urbanas utilizando drones autônomos. Esses drones transportam diferentes tipos de carga, operam sob condições ambientais distintas e devem permitir evolução futura do sistema. O objetivo desta correção orientada não é produzir uma única “solução correta”, mas avaliar decisões de modelagem — isto é, a qualidade estrutural do modelo proposto.

Objetivo

Delimitar o domínio e explicitar critérios de avaliação: clareza de abstrações, responsabilidades consistentes e preparação para mudança.

O que se espera alcançar

Que o estudante consiga justificar escolhas de modelagem com base em responsabilidade, coesão, acoplamento e extensibilidade.

Drones com capacidades distintas Entregas (expressa, médica, econômica) Sensores e clima Evolução futura do sistema

2. Identificando abstrações fundamentais

O primeiro passo de qualquer modelagem orientada a objetos é identificar entidades do domínio que apareçam naturalmente no problema. Em geral, emergem conceitos como Drone, Entrega, Pacote, Rota, Sensor e Clima. A ideia é representar conceitos do mundo real como abstrações computacionais com estado e comportamento. 

+----------------+     +----------------+     +----------------+
|     Drone      |     |     Entrega    |     |     Sensor     |
+----------------+     +----------------+     +----------------+
| id             |     | id             |     | tipo           |
| bateria        |     | pacote         |     | valor          |
| capacidade     |     | rota           |     +----------------+
| sensores[]     |     | prioridade(*)  |     | lerDados()     |
+----------------+     +----------------+     +----------------+
| voar()         |     | calcularPrazo()| 
| calcularRota() |     | calcularCusto()|
| monitorarBat() |     +----------------+
+----------------+

(*) prioridade tende a variar: candidata a estratégia (composição).
Objetivo

Aprender a partir do enunciado a extrair um “núcleo” de abstrações do domínio, evitando antecipar detalhes de implementação.

O que se espera alcançar

Um modelo inicial que permita discussão: o que é central, o que é acessório e onde haverá variação.

3. Analisando responsabilidades de cada abstração: o caso da classe Drone

Uma vez identificadas as abstrações, o passo seguinte é traduzir responsabilidades em atributos (estado) e métodos (comportamento). A pergunta guia é: “se existe uma classe Drone, o que ela deveria saber e o que deveria fazer?”. No domínio, responsabilidades típicas incluem voar, calcular rota, monitorar bateria e transportar carga. 

+------------------------------+
|            Drone             |
+------------------------------+
| capacidadeCarga : double     |
| bateria        : double      |
| sensores       : List|
+------------------------------+
| voar()                       |
| calcularRota(destino)        |
| monitorarBateria()           |
| transportarCarga(pacote)     |
+------------------------------+
            1
            |
          possui
            |
           0..*
+----------------+
|     Sensor     |
+----------------+
| tipo           |
| valor          |
+----------------+
| lerDados()     |
+----------------+
Objetivo

Demonstrar a ligação entre responsabilidade e design: o que a classe “assume” determina seus atributos e operações.

O que se espera alcançar

Um Drone que seja coeso: dados e operações relacionadas ao voo e ao monitoramento pertencem ao próprio objeto.

Pseudocódigo comentado

O pseudocódigo abaixo ilustra como responsabilidades podem ser expressas como operações do próprio objeto, preservando coesão. O foco não é a sintaxe, mas o encapsulamento da lógica essencial. 

classe Drone {

    privado capacidadeCarga
    privado bateria
    privado sensores : Lista

    metodo voar() {
        // Responsabilidade: executar voo (nível alto; detalhes ficam em módulos de navegação)
        consumirBateria(estimativaConsumoBasica())
    }

    metodo calcularRota(destino) {
        // Responsabilidade: delegar a decisão de rota
        // (pode evoluir para usar estratégia Roteamento)
        retornar Rota.basica(geoAtual(), destino)
    }

    metodo monitorarBateria() {
        // Responsabilidade: avaliar estado e acionar alertas
        se (bateria < 0.15) {
            emitirAlerta("Bateria crítica")
        }
    }

    metodo transportarCarga(pacote) {
        // Invariante: não exceder capacidade
        se (pacote.peso > capacidadeCarga) {
            lançar ErroDominio("Carga excede capacidade do drone")
        }
        // Ação de transporte pode depender de rota, clima e sensores
    }

    metodo consumirBateria(valor) { bateria = max(0, bateria - valor) }
}

4. Identificando pontos de variação no domínio

Um passo decisivo para modelagem orientada a objetos é identificar onde o sistema tende a variar. Pontos de variação são aspectos do domínio que podem mudar com frequência ou se multiplicar em tipos/regra. Em geral, são locais em que herança, polimorfismo e/ou composição serão considerados. 

Pontos de variação típicos:
  1) Tipo de drone
  2) Tipo/regra de entrega (prioridade)
  3) Tipo de sensor
  4) Condições ambientais (clima)

Esses pontos indicam “locais” onde o modelo deve ser preparado para mudança.
Objetivo

Ensinar a reconhecer variação antes de escolher mecanismos (herança vs composição), reduzindo retrabalho estrutural.

O que se espera alcançar

Um mapa de evolução: decisões arquiteturais passam a ser tomadas com base em onde o sistema mudará.

5. Variação 1: tipos de drone — quando herança pode fazer sentido

Para tipos de drone (leve, pesado, longa distância, médico), herança pode ser apropriada quando as diferenças forem especializações estruturais e a relação “é-um” for legítima. Isto é, cada tipo continua sendo um Drone e preserva propriedades esperadas do tipo base. 

                Drone
                  |
     ---------------------------------
     |               |               |
   DroneLeve   DroneCargaPesada  DroneLongaDistancia
                                   |
                                DroneMedico (opcional)
Critério prático.

Herança é mais defensável quando a variação muda limites/capacidades estruturais (carga máxima, alcance, sensores obrigatórios), e não apenas “políticas” ou regras combinatórias.

Pseudocódigo comentado

A seguir, um exemplo de especialização estrutural: drones variam por capacidade e alcance. O tipo base define um contrato mínimo e subclasses refinam limites, mantendo coerência. 

classe Drone {
    protegido capacidadeCargaMax
    protegido alcanceMaxKm

    metodo podeAceitar(pacote, distanciaKm) {
        retornar (pacote.peso <= capacidadeCargaMax) e (distanciaKm <= alcanceMaxKm)
    }
}

classe DroneLeve herda Drone {
    construtor() { capacidadeCargaMax = 2; alcanceMaxKm = 10; }
}

classe DroneCargaPesada herda Drone {
    construtor() { capacidadeCargaMax = 20; alcanceMaxKm = 8; }
}

classe DroneLongaDistancia herda Drone {
    construtor() { capacidadeCargaMax = 5; alcanceMaxKm = 120; }
}

6. Variação 2: tipos de entrega — risco de herança e explosão combinatória

Tipos de entrega (expressa, médica, econômica) podem ser modelados como subclasses, mas essa decisão costuma introduzir rigidez se, no futuro, múltiplas características precisarem coexistir (por exemplo, “médica e expressa ao mesmo tempo”). Nesses casos, a hierarquia tende a explodir em combinações, e o modelo perde flexibilidade. 

EntregaExpressa
EntregaMedica
EntregaEconomica

(Quando surgem combinações)
EntregaMedicaExpressa
EntregaEconomicaExpressa
EntregaMedicaEconomica
... (crescimento combinatório)
Objetivo

Mostrar que “tipo de entrega” frequentemente é uma regra de prioridade (comportamento variável), não identidade estrutural.

O que se espera alcançar

Que o estudante reconheça quando migrar de herança para composição para evitar rigidez e facilitar evolução.

7. Modelagem por composição: Entrega + Estratégia de Prioridade

Uma alternativa robusta é separar a entidade Entrega da regra de priorização. A entrega não “é” expressa ou médica; ela usa uma estratégia de prioridade que pode variar independentemente. Isso permite introduzir novas regras (VIP, hospitalar etc.) sem modificar a classe Entrega, alinhando-se ao princípio aberto-fechado (OCP). 

+----------------------+
|        Entrega       |
+----------------------+
| id                   |
| prazo                |
| prioridade : PrioridadeEntrega |
+----------------------+
| calcularPrioridade() |
+----------------------+
          |
       composição
          |
          v
+---------------------------+
|     PrioridadeEntrega     |
+---------------------------+
| calcularPrioridade(e)     |
+---------------------------+
     ^          ^           ^
     |          |           |
PrioridadeExpressa  PrioridadeMedica  PrioridadeEconomica
Objetivo

Evidenciar composição como mecanismo preferencial para comportamento variável, evitando explosão de subclasses.

O que se espera alcançar

Um modelo extensível: novas prioridades são adicionadas por novas classes, sem alterar Entrega.

Pseudocódigo comentado

O pseudocódigo abaixo ilustra delegação: Entrega preserva identidade e delega a priorização a uma estratégia. 

interface PrioridadeEntrega {
    metodo calcularPrioridade(entrega) : inteiro
}

classe PrioridadeExpressa implementa PrioridadeEntrega {
    metodo calcularPrioridade(entrega) {
        // Expressa: prioriza tempo (prazo menor => prioridade maior)
        retornar 100 - entrega.prazoEmMinutos()
    }
}

classe PrioridadeMedica implementa PrioridadeEntrega {
    metodo calcularPrioridade(entrega) {
        // Médica: prioriza segurança (pode ponderar risco/clima/rota)
        retornar 1000
    }
}

classe PrioridadeEconomica implementa PrioridadeEntrega {
    metodo calcularPrioridade(entrega) {
        // Econômica: prioriza custo (pode preferir rotas mais baratas)
        retornar 10
    }
}

classe Entrega {
    privado prioridade : PrioridadeEntrega
    privado prazo

    metodo calcularPrioridade() {
        // Delegação: Entrega não codifica todas as regras; ela usa uma estratégia
        retornar prioridade.calcularPrioridade(this)
    }
}
Regra de decisão.

Herança tende a representar “o que algo é”. Composição tende a representar “o que algo usa para se comportar”.

8. Variação 3: sensores e condições climáticas — composição + polimorfismo

Sensores representam capacidades adicionais que um drone possui. Por isso, modelá-los como componentes (o drone tem sensores) tende a ser mais flexível do que transformar cada combinação em subclasse de Drone. Cada sensor implementa um contrato comum, de modo que o drone não precisa conhecer detalhes de tipos específicos. 

+------------------------------+
|            Drone             |
+------------------------------+
| sensores : List      |
+------------------------------+
| voar()                       |
| monitorarBateria()           |
+------------------------------+
             |
           possui
             |
            0..*
+------------------+
|      Sensor      |
+------------------+
| lerDados()       |
+------------------+
   ^       ^        ^         ^
   |       |        |         |
SensorGPS SensorVento SensorTemperatura SensorObstaculo
Objetivo

Demonstrar como interfaces + composição permitem adicionar novos sensores sem alterar a classe Drone.

O que se espera alcançar

Um Drone que opera sobre o contrato Sensor, mantendo baixo acoplamento com tipos concretos.

Pseudocódigo comentado

A seguir, um exemplo de leitura polimórfica: o drone percorre sensores e coleta dados de forma uniforme. 

interface Sensor {
    metodo lerDados() : Medicao
}

classe SensorGPS implementa Sensor {
    metodo lerDados() { retornar Medicao("gps", lerCoordenadas()) }
}

classe SensorVento implementa Sensor {
    metodo lerDados() { retornar Medicao("vento", velocidadeVento()) }
}

classe Drone {
    privado sensores : Lista

    metodo coletarTelemetria() : Lista {
        telemetria = []
        para cada s em sensores {
            // Polimorfismo: mesma mensagem, diferentes implementações
            telemetria.adicionar(s.lerDados())
        }
        retornar telemetria
    }
}

Consequência arquitetural: se surgir “SensorPressaoAtmosferica”, ele pode ser adicionado criando-se uma nova classe que implementa Sensor, sem necessidade de modificar Drone.

9. Evolução futura do sistema e impacto arquitetural

Uma validação importante do modelo é perguntar como ele se comporta diante de mudanças previsíveis. Por exemplo: se surgirem drones aquáticos, drones híbridos ou novas políticas regulatórias, quais partes do sistema precisarão ser alteradas? Se a hierarquia for rígida e expressar variações combinatórias, mudanças tendem a afetar múltiplas classes. Se o modelo separar identidade estrutural de comportamento variável por interfaces e composição, mudanças tendem a ser localizadas.

Critério de qualidade.

Arquitetura OO pode ser entendida como estratégia para controlar o impacto da mudança: reduzir o “raio de explosão” de alterações futuras.

Objetivo

Conectar decisões de modelagem a custos de evolução: onde a mudança “bate” determina o custo de manutenção e refatoração.

O que se espera alcançar

Que o estudante consiga prever impacto de mudanças e preferir mecanismos que preservem extensibilidade.

10. Conclusão

A correção orientada enfatiza que o objetivo não é desenhar “classes perfeitas”, mas pensar estruturalmente. Em modelagem OO, o núcleo do raciocínio é decidir responsabilidades, reduzir complexidade por abstração e tomar decisões estruturais que determinam a capacidade de evolução do sistema. 

1) Modelar é decidir responsabilidades (quem faz o quê).
2) Abstração reduz complexidade (seleciona o que é relevante).
3) Boas decisões estruturais determinam evolução (custo de mudança futura).
